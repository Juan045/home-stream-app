Stream Media

Servicio auto-hospedado de streaming multimedia. Analiza el archivo de video, elige la estrategia óptima de procesamiento (remux o transcodificación), y lo entrega al navegador a través de HLS. El audio se entrega como rendition groups de HLS, así que cambiar de idioma es instantáneo y el seek es libre.

Resumen del proyecto

Stream Media es un servicio de streaming de contenido multimedia auto-hospedado, inspirado en plataformas como Jellyfin. El sistema resuelve un problema concreto: dado un archivo de video almacenado en disco, permitir su reproducción inmediata desde cualquier navegador en la red local, con la posibilidad de elegir entre las pistas de audio y subtítulos disponibles en el archivo.

El flujo comienza cuando el usuario proporciona la ruta de un archivo — por ejemplo /home/peliculas/peli.mkv. El sistema analiza el archivo usando ffprobe para detectar el codec de video, las pistas de audio disponibles (con sus idiomas y codecs) y las pistas de subtítulos. Con esta información, determina la estrategia óptima: remux sin re-codificación (para H.264) o transcodificación a H.264 (para H.265 u otros codecs). El procesamiento inicia inmediatamente con la primera pista de audio y sin subtítulos.

El contenido se entrega al navegador como HLS en todos los casos. El video se segmenta sin audio y cada pista de audio por separado, todas con el mismo origen de tiempo; el master las declara como renditions. Gracias a eso el usuario puede cambiar de idioma sin perder la posición y sin corte de video, activar subtítulos en cualquier momento, y navegar libremente por la línea de tiempo. Los artefactos quedan cacheados por archivo, de modo que la segunda apertura es inmediata.

Esta primera iteración se centra en el motor de procesamiento, entrega y selección de pistas. No incluye biblioteca de medios, autenticación ni interfaz de gestión — es el núcleo funcional sobre el que se construirá todo lo demás.

Alcance del MVP

Incluido

  • Recibir ruta de archivo local como entrada
  • Detección automática de codec, contenedor, pistas de audio y subtítulos con ffprobe
  • Remux para H.264 en cualquier contenedor (sin re-codificación de video)
  • Transcodificación H.264 + AAC para H.265 y otros codecs
  • Entrega HLS para todos los casos
  • Selección de pista de audio por el usuario
  • Subtítulos de texto (SRT, ASS) extraídos a WebVTT
  • Seek libre — codificación desde cualquier punto de la línea de tiempo
  • Reproductor web integrado con hls.js
  • Gestión automática de archivos temporales
  • Progreso de procesamiento en tiempo real
  • API REST para gestionar operaciones

Futuro

  • Adaptive Bitrate Streaming (ABR)
  • Codec AV1
  • Subtítulos de imagen (PGS, VOBSUB)
  • Encoding por hardware (NVENC, VA-API, AMF)
  • Autenticación y control de acceso
  • Biblioteca y escaneo de medios
  • Segmentos fMP4 (.m4s) como alternativa a .ts
Formatos soportados: .mp4 y .mkv como contenedores principales. Codecs de entrada: H.264 y H.265. Subtítulos de texto: SRT y ASS/SSA (convertidos a WebVTT). Otros contenedores (.avi, .mov, .webm), codecs y subtítulos de imagen se consideran futuros.

Requerimientos

Funcionales

RF-01 Recibir una ruta absoluta de archivo de video como entrada a través de la API REST.
RF-02 Validar que el archivo existe en disco y que su extensión es soportada (.mp4, .mkv).
RF-03 Analizar el archivo con ffprobe para detectar el codec de video, todas las pistas de audio (codec, idioma, canales) y todas las pistas de subtítulos (formato, idioma).
RF-04 Determinar automáticamente la estrategia de procesamiento basada en el codec de video: remux (H.264) o transcodificación (H.265 u otros).
RF-05 Remuxear archivos H.264 (cualquier contenedor) sin re-codificación de video, mapeando la pista de audio seleccionada y generando segmentos HLS (.ts) y manifest (.m3u8).
RF-06 Transcodificar archivos H.265 (u otros codecs no soportados) a H.264 + AAC, mapeando la pista de audio seleccionada y generando segmentos HLS.
RF-07 Iniciar el procesamiento automáticamente con la primera pista de audio disponible y sin subtítulos.
RF-08 Proveer al usuario la lista de pistas de audio y subtítulos disponibles en el archivo.
RF-09 Permitir al usuario cambiar la pista de audio durante la reproducción. El sistema detiene el proceso FFmpeg actual y reinicia con la pista seleccionada.
RF-10 Permitir al usuario activar, cambiar o desactivar subtítulos durante la reproducción. Los subtítulos de texto (SRT, ASS) se extraen a WebVTT bajo demanda, sin reiniciar FFmpeg.
RF-11 Permitir seek libre: el usuario puede navegar a cualquier punto de la línea de tiempo. El sistema detiene FFmpeg y reinicia la codificación desde el timestamp solicitado usando -ss.
RF-12 Servir los segmentos HLS y el manifest a través de HTTP en un puerto configurable.
RF-13 Proveer un reproductor web embebido que reproduzca el contenido usando hls.js, con controles para selección de pista de audio y subtítulos.
RF-14 Reportar el progreso de procesamiento como porcentaje, consultable vía API.
RF-15 Permitir consultar el estado de todos los jobs (pendiente, procesando, listo, fallido).
RF-16 Permitir iniciar la reproducción antes de que el procesamiento termine — los primeros segmentos HLS se sirven mientras FFmpeg genera los restantes.
RF-17 Eliminar automáticamente los archivos temporales (segmentos HLS, subtítulos) cuando la sesión de visualización termina.
RF-18 Limitar el número de procesos FFmpeg concurrentes a un máximo configurable (por defecto: 2).

No funcionales

RNF-01 Para remux, el primer segmento HLS debe estar disponible en menos de 5 segundos.
RNF-02 La extracción de un subtítulo de texto a WebVTT debe completarse en menos de 2 segundos.
RNF-03 El sistema debe soportar al menos 5 streams simultáneos de reproducción.
RNF-04 Los segmentos HLS deben tener una duración de 6 segundos, alineada con la recomendación de Apple.
RNF-05 El servicio debe funcionar en Linux y Windows sin modificaciones al código.
RNF-06 Logs estructurados (JSON) con niveles de severidad para facilitar monitoreo y debugging.
RNF-07 El espacio en disco temporal no debe exceder un límite configurable (SM_MAX_CACHE_SIZE, por defecto: 50 GB).
RNF-08 Tras un seek o cambio de pista de audio, el primer segmento debe estar disponible en menos de 5 segundos para remux y menos de 15 segundos para transcodificación.

Arquitectura del sistema

El diagrama de componentes de esta sección todavía muestra el flujo anterior, con un job_manager que reiniciaba FFmpeg ante cada cambio de pista. Los módulos actuales son asset_store, asset_builder, playlist y session_manager; ver Implementación → Estructura del proyecto.

El sistema se compone de cinco elementos principales: el archivo de video como entrada, un analizador que detecta codec, pistas de audio y subtítulos mediante ffprobe, un router que selecciona la estrategia de procesamiento (remux o transcodificación), un worker de FFmpeg que ejecuta el procesamiento, y un servidor FastAPI que orquesta todo el proceso y sirve el contenido al navegador.

Diagrama de componentes

El Servidor FastAPI es el componente central. Cumple cinco funciones: expone la API REST para recibir solicitudes, invoca al analizador para determinar la estrategia y las pistas disponibles, orquesta los procesos de FFmpeg para remux o transcodificación, gestiona la selección de pistas de audio y subtítulos por parte del usuario, y sirve el contenido al navegador como segmentos HLS y archivos WebVTT.

El Analizador usa ffprobe para inspeccionar el archivo de video y extraer toda la información de sus streams: codec de video, cada pista de audio (con codec, idioma, número de canales y título) y cada pista de subtítulos (con formato e idioma). Con esta información, determina la estrategia de procesamiento y provee las opciones disponibles al usuario.

El Sesión Manager lleva la cuenta de quién está mirando qué. Monitorea la actividad del cliente mediante heartbeats y aplica un TTL de inactividad; su efecto práctico es proteger del recolector a los assets que alguien está usando. No gestiona procesos de FFmpeg: cambiar de pista de audio y hacer seek son operaciones del cliente y no lo involucran.

Flujo de datos

API REST

Los endpoints de control están bajo /api/v1. Las playlists y los segmentos se sirven bajo /hls. El reproductor está en /static/player.html.

No hay endpoint para cambiar de pista de audio ni para hacer seek. El master declara las pistas de audio como renditions y el timeline es absoluto, así que las dos cosas las resuelve el cliente sin volver al servidor.
POST /api/v1/stream

Abre un archivo. Si sus artefactos ya están en el cache no genera nada; si no, lanza el build del video y el de cada pista de audio, y extrae los subtítulos. Retorna apenas hay segmentos suficientes para empezar a reproducir, sin esperar a que el build termine.

Request body

{
  "file_path": "/home/peliculas/peli.mkv"
}

Response — 201 Created

  "session_id": "a3f9c1d20e84",
  "asset_id": "9f2b7c1d4e6a8b30",
  "status": "processing",
  "master_url": "/hls/9f2b7c1d4e6a8b30/master.m3u8",
  "duration_seconds": 7245.3,

    { "index": 0, "codec": "ac3", "channels": 6, "language": "spa", "title": "Español" },
    { "index": 1, "codec": "aac", "channels": 2, "language": "eng", "title": "English" }

Errores

400 ruta inválida, extensión no soportada, path traversal o fuera de MEDIA_ROOT · 404 el archivo no existe · 503 se alcanzó MAX_CONCURRENT_FFMPEG · 507 el cache está lleno y el GC no pudo liberar nada.

GET /api/v1/sessions/{session_id}

Estado actual del build. Misma forma que la respuesta de POST /api/v1/stream. El player la consulta cada 2 s mientras status sea processing, para mover la barra de progreso.

404 si la sesión expiró o si su asset ya no está disponible.

POST /api/v1/heartbeat/{session_id}

Mantiene viva la sesión y corre a su asset al frente del LRU. El player lo llama cada 30 segundos. Responde 204 No Content, o 404 si la sesión ya no existe.

GET /hls/{asset_id}/master.m3u8

Master playlist. Declara el video y una rendition de audio por pista generada.

#EXTM3U
#EXT-X-VERSION:7
#EXT-X-INDEPENDENT-SEGMENTS
#EXT-X-MEDIA:TYPE=AUDIO,GROUP-ID="aud",NAME="Español",LANGUAGE="spa",DEFAULT=YES,AUTOSELECT=YES,CHANNELS="2",URI="audio/0/playlist.m3u8"
#EXT-X-MEDIA:TYPE=AUDIO,GROUP-ID="aud",NAME="English",LANGUAGE="eng",DEFAULT=NO,AUTOSELECT=YES,CHANNELS="2",URI="audio/1/playlist.m3u8"
#EXT-X-STREAM-INF:BANDWIDTH=4500000,RESOLUTION=1920x1080,CODECS="avc1.640029,mp4a.40.2",AUDIO="aud"
video/playlist.m3u8
GET /hls/{asset_id}/video/playlist.m3u8 /hls/{asset_id}/audio/{n}/playlist.m3u8

Media playlists. Se calculan en cada request a partir de las duraciones reales que FFmpeg fue escribiendo en su internal.m3u8; ese archivo interno nunca se sirve.

#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:6
#EXT-X-MEDIA-SEQUENCE:0
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MAP:URI="init.mp4"
#EXTINF:6.000000,
seg-00000.m4s
...
#EXT-X-ENDLIST

Mientras el build corre se emite como EVENT y sin #EXT-X-ENDLIST. Al terminar pasa a VOD y el archivo queda seekeable entero.

GET /hls/{asset_id}/**

Segmentos (.m4s), init segments (init.mp4) y subtítulos (.vtt), servidos como archivos estáticos. Los segmentos van con Cache-Control: immutable; las playlists, con no-store.

El router se registra antes de este montaje. Starlette resuelve en orden de registro: si el montaje estático ganara, se serviría el internal.m3u8 de FFmpeg en lugar de la playlist calculada. Es un fallo silencioso y hay un test dedicado a impedirlo.

Pipeline de procesamiento

Detección de codec y pistas

El análisis se hace con una sola invocación de ffprobe:

ffprobe -v quiet -print_format json -show_streams -show_format archivo.mkv

De ahí salen el codec de video con su perfil y nivel, la duración, el bitrate, y la lista completa de pistas de audio y subtítulos con sus idiomas, codecs, canales y títulos. El resultado se serializa en manifest.json dentro del cache: reabrir el mismo archivo no vuelve a ejecutar ffprobe.

Timeline absoluto

Esta es la invariante de la que depende todo lo demás. El video, cada pista de audio y los subtítulos se generan en corridas separadas de FFmpeg. Que compartan el mismo origen de tiempo es lo único que los mantiene sincronizados.

-copyts -avoid_negative_ts disabled -muxdelay 0 -muxpreload 0

-copyts evita que FFmpeg rebasee los PTS a cero. -muxdelay y -muxpreload en cero impiden que el muxer agregue su preload por defecto, que correría el timeline unos cientos de milisegundos.

Nunca agregar -output_ts_offset: con -copyts los PTS ya salen absolutos y sumarlo otra vez los duplica. Nunca agregar -start_at_zero: contradice a -copyts. Un segmento del minuto 2 debe declarar PTS ≈ 120; si declara 0 falta -copyts, y si declara 240 se coló -output_ts_offset.

Video y audio en pistas separadas

El video se segmenta sin audio (-an) y cada pista de audio sin video (-vn). El master las declara con #EXT-X-MEDIA:TYPE=AUDIO.

La consecuencia práctica es que cambiar de idioma pasa a ser hls.audioTrack = n en el cliente: no se recarga el manifest, no se pierde currentTime, no se reinicia FFmpeg, no se resetean los subtítulos y no hay corte de video.

El audio-only corre a unas 200 veces el tiempo real, así que todas las pistas se construyen de entrada, en paralelo con el video. Terminan mucho antes que él, de modo que cuando el usuario quiere cambiar de idioma la rendition ya está lista.

Niveles de procesamiento del video

El sistema elige la ruta de menor costo para el video. La salida siempre es HLS en fMP4.

# Remux (H.264 compatible)
ffmpeg -nostdin -hide_banner -nostats -loglevel error -progress pipe:1 \
  -copyts -i entrada.mkv \
  -map 0:v:0 -an -sn -dn -map_chapters -1 \
  -c:v copy \
  -avoid_negative_ts disabled -muxdelay 0 -muxpreload 0 \
  -f hls -hls_time 6 -hls_playlist_type vod \
  -hls_segment_type fmp4 -hls_fmp4_init_filename init.mp4 \
  -hls_flags independent_segments \
  -hls_segment_filename video/seg-%05d.m4s \
  -y video/internal.m3u8

# Transcodificación (H.265 u otros), reemplaza el bloque -c:v
  -c:v libx264 -preset veryfast -crf 23 -maxrate 4000k -bufsize 8000k \
  -pix_fmt yuv420p -profile:v high -level 4.1 \
  -vf scale=-2:'min(1080,ih)' \
  -force_key_frames expr:gte(t,n_forced*6) -sc_threshold 0

-force_key_frames pone un keyframe en cada borde de segmento y -sc_threshold 0 desactiva los keyframes por cambio de escena, que podrían correr los cortes. Así las duraciones salen exactas sin necesidad de indexar los keyframes del origen.

Para el audio: -c:a copy si la pista ya es AAC con la cantidad de canales de salida; en cualquier otro caso -c:a aac -b:a 128k -ac 2.

Las playlists se calculan, no se sirven

FFmpeg escribe un internal.m3u8 por pista. Ese archivo nunca llega al cliente: solo se parsea para conocer las duraciones reales de los segmentos. Las playlists que ve el navegador las arma el módulo playlist.py, que es lógica pura y no toca disco.

Declarar #EXTINF:6.000 uniforme cuando los segmentos reales no lo son desfasa los subtítulos, y el error se acumula con el tiempo de reproducción. Leer las duraciones de la salida de FFmpeg hace que la playlist sea verdadera por construcción, sin necesidad de un índice previo de keyframes.

Las media playlists de dos idiomas distintos son idénticas salvo la URI base. Eso es lo que garantiza que el timeline no cambie al cambiar de audio.

Extracción de subtítulos

Cada pista se extrae una vez a WebVTT y se sirve como archivo estático, completamente fuera del pipeline de audio:

ffmpeg -i entrada.mkv -map 0:s:{n} -c:s webvtt -y subs/sub_{n}_{lang}.vtt

Los tiempos del VTT son absolutos respecto del original, igual que los de los segmentos, así que la sincronización se mantiene en cualquier posición. El player los carga como elementos <track>.

PGS y VobSub son formatos de mapa de bits, típicos de rips de Blu-ray y DVD: la extracción falla. El error se registra y el sistema sigue sin esa pista, en lugar de abortar la apertura del archivo.

Seek

No requiere nada del servidor. Con la playlist en VOD el player conoce todos los segmentos y puede saltar a cualquier punto pidiendo el segmento correspondiente. Mientras el build corre y la playlist es EVENT, el rango disponible es el ya generado; el player avisa si el usuario intenta ir más allá.

Monitoreo de progreso

FFmpeg se invoca con -progress pipe:1, que emite bloques de estado por stdout. Se lee out_time_us (y su duplicado out_time_ms, que se descarta) para saber cuántos segundos de video se procesaron, y de ahí sale el progress que consume el player.

Gestión de almacenamiento

El directorio de salida es un cache persistente, no un temporal. No se borra al arrancar: abrir dos veces la misma película no debería costar volver a generarla. Lo que se controla es su tamaño.

Assets y sesiones

Son dos cosas distintas y conviene no volver a mezclarlas:

  • Asset: un archivo de origen y sus artefactos derivados. Su identidad es (ruta, mtime, tamaño), así que reemplazar el archivo invalida el cache solo. Vive en disco y sobrevive entre arranques.
  • Sesión: un espectador. Efímera, con heartbeat y TTL. No es dueña de ningún archivo; lo único que hace es proteger a su asset del recolector.

Mecanismo 1: LRU con tope de tamaño

Cada asset registra cuándo se usó por última vez. Cuando el cache supera SM_MAX_CACHE_SIZE, se borran los assets menos usados recientemente que no tengan sesiones vivas ni builds en curso. Si lo único que queda está protegido, el recolector se detiene: es preferible pasarse del tope a cortarle la reproducción a alguien.

Un asset borrado se saca también de memoria; de lo contrario se seguirían sirviendo playlists que apuntan a segmentos que ya no existen.

Mecanismo 2: Heartbeat + TTL

El player envía POST /api/v1/heartbeat/{session_id} cada 30 segundos. Dos minutos sin heartbeat marcan la sesión como inactiva — deja de proteger su asset, pero se conserva por si el usuario vuelve. A los 12 minutos se elimina.

Mecanismo 3: Ciclo periódico

Una tarea de fondo corre cada SM_CLEANUP_INTERVAL segundos: poda las sesiones expiradas y aplica el LRU. Es el único mecanismo que libera espacio, así que no puede morirse por una excepción suelta.

Rechazo por falta de espacio

Antes de abrir un archivo que no esté ya cacheado ni abierto, se intenta liberar espacio. Si aún así el cache sigue por encima del tope, la apertura se rechaza con 507. Si hay demasiados builds en curso, con 503. Un archivo ya cacheado o ya abierto nunca se rechaza: no genera trabajo nuevo.

Configuración

Todas las opciones se configuran vía variables de entorno, con valores por defecto sensatos:

# Servidor
HOST=0.0.0.0
PORT=8000

# Rutas
SM_MEDIA_ROOT=/home/peliculas     # Directorio base permitido (opcional)
SM_CACHE_DIR=./output             # Cache de artefactos (persistente)

# FFmpeg
SM_HLS_TIME=6                     # Duración de segmento en segundos
SM_FFMPEG_PRESET=veryfast         # Preset de libx264 para transcodificación
SM_FFMPEG_CRF=23                  # Calidad de transcodificación
SM_AUDIO_BITRATE=128k             # Bitrate del AAC de salida
SM_AUDIO_CHANNELS=2               # Canales de audio de salida
SM_MAX_CONCURRENT_FFMPEG=3        # Máximo de procesos FFmpeg simultáneos

# Sesión y limpieza
SM_SESSION_INACTIVE_AFTER=120     # Segundos sin heartbeat para marcar inactiva
SM_SESSION_EXPIRE_AFTER=720       # Segundos sin heartbeat antes de eliminar
SM_CLEANUP_INTERVAL=60            # Segundos entre ciclos de limpieza
SM_MAX_CACHE_SIZE=53687091200     # 50 GB en bytes

FFmpeg y ffprobe son dependencias del sistema — deben estar instalados y accesibles en el PATH. No se usa una librería wrapper de Python para FFmpeg; la invocación directa via asyncio.create_subprocess_exec da control total sobre los argumentos, el manejo de la salida y la capacidad de detener los procesos al apagar el servidor.
